# panel — 審査員パネル（マルチエージェント最終関門）

> **▶ 実行開始時の共通3点セット**（詳細 → `~/.claude/skills/shared-doc-rules/SKILL.md` §8〜§10）
> 1. 📢 **公言**：応答冒頭で「panel スキルを使っています」と必ず出力する（§10）
> 2. 🎯 **イシューからはじめよ**：「この成果物は何点なら出せるか・どこで落ちるか」を先に決めてから審査する（§8）
> 3. 🚫 **AIっぽさ撲滅**：講評自体も定型句を使わない（§9）
> 4. `~/.claude/skill-memory/panel.md` があれば読む

成果物を**専門エージェントの合議**にかける。1人のレビューでは出ない多面的な指摘を、提出直前に一度で回収する。審査員はこのリポジトリの `agents/*.md` を `~/.claude/agents/` にコピーしておくと `subagent_type` で呼べる（運用規律を `~/.claude/agents/README.md` に書いている環境ならそれにも従う）。

## STEP 0: 成果物の種類判定と審査員の選任

| 成果物 | 召集する審査員（subagent_type） |
|---|---|
| 実験レポート (.docx) | `grader`（要領基準の採点）＋`adversarial-verifier`（数値の出所）。計算・誤差率が多い回は`math-checker`（検算）を足す。（任意）提出先の先生の好みを持たせた審査役を自分で作っていれば加えて4人まで |
| スライド (.pptx/_all.png) | `slide-reader`（文字だけで意味が通るか。渡すのは `claims.py --reader` が書く `<proj>/review/slide_text.md` と聴衆の1行だけ）＋`slide-evidence-checker`（結論と証拠の噛み合い。渡すのは `<proj>/review/claims.json` と素材の絶対パスだけ＝画像は渡さない）＋`slide-critic`（8観点）＋`fact-checker`（データ枚の出典）。（任意）発表先の先生の好みを持たせた審査役を自分で作っていれば、発表先が学内の時に加える。**slide-gen の段階で R0・R1 が今の hash で PASS 済み（`deck_doctor` に R0・R1 が出ない）なら、その2人は呼ばずに `review/evidence_check.md`・`review/reader_check.md` を講評に使い**、空いた枠で fact-checker と（あれば）先生役の審査員を呼ぶ |
| ES・自己PR・LinkedIn投稿 | `fact-checker`（実績の裏取り）＋`adversarial-verifier`（盛り検出）＋`copy-editor`（深層のAIくささ・文体）。（任意）AIくささの機械検査スクリプトを持っていれば併用 |
| 企画書・提案書・報告書 | `fact-checker`＋`adversarial-verifier`＋`copy-editor`（提出先の先生の好みを持たせた審査役を自分で作っていれば、学内提出の時はそちらでもよい） |

- 種類が不明なら中身を読んで判定。提出先（教授名・企業・公開先）が分かれば審査員のプロンプトに渡す。
- 迷ったら3人。**多くても4人まで**（指摘の重複が増えるだけ）。

## STEP 1: 事前の機械ゲート（人手の前に必ず）

- 文章系: （任意）AIくささの機械検査スクリプトを持っていれば回して 0件に（このリポジトリには含まれない。無ければ飛ばし、copy-editor の目視に任せる）
- 実験レポート: `py ~/.claude/skills/report/scripts/run_pipeline.py` を 3種 [OK] に
- スライド: `svg_quality_checker.py`（ppt-master 同梱）error 0 ＋ slide-gen の `preview.ps1` で `_all.png` 生成
機械で落ちる状態でパネルを呼ばない（審査員の時間を機械検出可能な指摘で浪費しない）。

## STEP 2: パネル召集（並列）

**1メッセージで全審査員を並列起動**（Agent ツール・`subagent_type` に上表の名前）。起動前に、各審査員に①成果物のフルパス ②文脈〈テーマ・提出先・要領PDFパス等〉③出力形式 ④仮定してよいこと、を全部渡す（渡し忘れは審査員でなく親の失敗）。ultracode 有効時や大規模時は Workflow の並列＋敵対的検証パターンでもよい。

## STEP 3: 統合講評（親がやる・エージェントに任せない）

1. 全審査員の指摘を回収し、**重複を統合**（同じ穴を別語で指摘した物は1つに）。
2. **矛盾する指摘は親が裁定**（例: graderは「説明を足せ」・criticは「削れ」→ 成果物の目的で決める）。
3. インパクト×手間で並べた **「直す順リスト」Top5〜10** を作る。
4. 総合判定を1行で: **このまま提出可 ／ 直せば可（所要目安） ／ 作り直し**。

## STEP 4: 出力と完了

1. 判定1行 → 直す順リスト → 審査員別の講評（要約）の順で提示。
2. ユーザーが「直して」と言えばリスト順に修正し、**修正後に同じパネルを再召集**（1回まで。2回通らなければ設計の問題として報告）。
3. `~/.claude/skill-memory/panel.md` に「効いた審査員の組合せ・裁定に迷った矛盾」を追記（最大10件）。

## 注意事項

- パネルは**提出直前の最終関門**。制作の途中で呼ばない（各スキル内の品質ループで回す）。
- 審査員の指摘も鵜呑みにしない（slide-gen の教訓: 群れゲーにヒットストップ、のような文脈無視の提案は親が棄却する）。
- 数値・実績の指摘で審査員が「代替値」を提案しても、**捏造禁止が常に優先**（無い数値は空欄か削除）。
- サブエージェントのセッション上限に達している場合は、審査員の人格プロンプト（`~/.claude/agents/*.md`）を自分で読み、**同じ観点を直列で自分に適用**する縮退モードで代替する。
