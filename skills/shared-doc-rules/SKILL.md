# 文書生成 共通ルール

このファイルは他のスキル（report, proposal, slide-gen 等）から参照される共通規約。
直接 `/shared-doc-rules` で呼び出すものではない。

---

## 1. ファイル命名規則

### バージョン管理
- **「最終版」「完成版」「final」は絶対に使わない**
- バージョン番号を `_v1`, `_v2`, `_v3` ... と末尾に付与する
- 同名ファイルが既に存在する場合、最大バージョン番号を検出して +1 する
- 例: `実験レポート_テーマ2_v1.docx` → `実験レポート_テーマ2_v2.docx`
- 付属物（PDF・ページ画像・pipeline_report・採点結果）も本体と同じ `_v{N}` を名前に入れる。番号が揃っていれば片づけの時に一緒に動く
- **低い版は自分で消さない・`旧版/` フォルダを作らない**。片づけるかは本人が決める（環境依存・任意: 古い版を自動でゴミ箱へ移すスクリプトを持っていれば、それに任せる）
- 提出した版・本人が残すと言った版は消さない
- **機械で止める**: `scripts/safe_save_path.py` の `safe_save_path()`（と `check_file_name()`）は、ファイル名に
  「最終版」「完成版」「final」（大文字小文字問わず。finals 等の別の英単語は除く）が入っているか、拡張子の前が
  `_v{N}`（時刻付きは `_v{N}_HHMMSS`）で終わっていなければ **ValueError** を投げる。下の「共有フォルダの例外」に登録したフォルダの配下は検査しない

### 命名テンプレート
```
{ドキュメント種別}_{タイトル or テーマ名}_v{N}.{拡張子}
```
- ドキュメント種別: `レポート`, `企画書`, `議事録`, `予算表`, `スライド` 等
- タイトル: 日本語OK、スペースはアンダースコアに置換
- 例:
  - `レポート_テーマ2_トランジスタ増幅回路_v1.docx`
  - `企画書_ハッカソン2026_v3.docx`
  - `議事録_サークル定例_20260417_v1.md`
  - `予算表_留学費用_v2.xlsx`
  - `スライド_半導体入門_v1.pptx`

### 共有フォルダの例外
チームの共有フォルダなど、別の命名規則が決まっている場所ではそちらに従う。
`safe_save_path` の検査から外すには、環境変数 `SAFE_SAVE_EXEMPT_DIRS` にフォルダ名の一部を `;` 区切りで書く
（例: `SAFE_SAVE_EXEMPT_DIRS=サークル共有;ゼミ共有`）。既定は空＝例外なし。

### タイムスタンプ（必要な場合のみ）
- 日付: `_YYYYMMDD` をタイトルの後、バージョンの前に挿入
- 時刻（OneDriveロック回避用）: `_HHMMSS` をバージョンの後に付与
- 例: `議事録_定例_20260417_v1.md`

## 2. 出力先ディレクトリ

ワークスペース（`<YOUR_WORKSPACE>`）配下の構成。**下は作者の構成例なので、自分のフォルダ構成に合わせて書き換える**
（プロジェクトの CLAUDE.md に構成を書いているなら、そちらが常に正）:

```
<YOUR_WORKSPACE>/                     # 作者の構成例
├── 10_学内/
│   ├── 10_授業/{学年}年{前期|後期}/{授業名}/   # 1年前期 … 4年後期（学年と学期を1階層に）
│   └── 20_{学内の活動名}/  30_留学/
├── 20_学外/
│   ├── {YYYYMMDD_イベント名}/
│   └── コンペ/{コンテスト名}/
├── 30_開発/{コードプロジェクト名}/
├── 40_ツール/{ツール名}/             # 単発スクリプトは 40_ツール/_スクリプト/
├── 50_プロジェクト/{プロジェクト名}/
├── 60_執筆・note/
└── 90_受信箱/  91_一時置き/  99_ゴミ箱/{YYYY-MM-DD}/
```

### 出力先の決定ロジック
1. ユーザーが明示的にパスを指定した場合 → そのパスに出力
2. 授業関連 → `<YOUR_WORKSPACE>/10_学内/10_授業/{学年}年{前期|後期}/{授業名}/`
3. コンペ関連 → `<YOUR_WORKSPACE>/20_学外/コンペ/{コンテスト名}/`
4. ツール・スクリプト → `<YOUR_WORKSPACE>/40_ツール/{ツール名}/`（単発スクリプトは `40_ツール/_スクリプト/`）
5. 不明な場合 → **作成前に**ユーザーに保存先を確認する。すぐ確認できない状況（無人実行等）では
   受信箱フォルダ（作者の構成では `90_受信箱/`）に保存して報告する。カレントディレクトリやワークスペース直下には出さない

## 3. OneDriveファイルロック対策

OneDrive上のファイルがWord/Excelで開かれていると `PermissionError` が発生する。

### 対策手順
1. 保存前にファイルの存在をチェック
2. 存在する場合、書き込み可能かテスト（try-except）
3. ロックされている場合:
   - バージョン番号を +1 して別名で保存
   - ユーザーに「{元ファイル}がロックされていたため {新ファイル} として保存しました」と報告

実装は `scripts/safe_save_path.py` の `safe_save_path(base_path)` を使う（命名規則の検査 → 存在チェック → 書き込みテスト → `_v{N}` インクリメントの順で安全なパスを返す。命名規則に反する名前は §1 のとおり ValueError）。
写しを作らず本体を import する（preview-report の `omml_lib.safe_save_path` も本体を呼ぶ）。回帰テストは `scripts/tests/test_safe_save_path.py`。

## 4. skill-memory 運用

全スキル共通で `~/.claude/skill-memory/{スキル名}.md` を運用する。

### 読み込みタイミング
- スキル実行開始時に必ず読み込む
- ファイルが存在しない場合はスキップ（初回実行）

### 書き込みタイミング
- スキル実行完了後に必ず更新する
- 今回の実行で学んだ改善点・注意点を追記する

### フォーマット
```markdown
# {スキル名} 改善メモ

## 改善履歴

### {日付}: {改善タイトル}
- **状況:** {何が起きたか}
- **改善:** {どう改善すべきか}
- **適用条件:** {いつこの改善を適用するか}
```

## 5. 生成ファイルの提示（自動オープン禁止）

- **成果物を画面で勝手に開かない**（運用で出た指摘「勝手に開かれて閉じないから邪魔」）
- 見せ方: **フルパスの提示**＋必要に応じて PNG/スクリーンショット化して Read で自分が確認した内容を報告する
- 開くのは**本人が「開いて」と言った時だけ**。その場合は `explorer.exe "{フルパス}"`
  （`start`/`rundll32` は日本語パス文字化けのため禁止）
- Word/PowerPoint COM を使う時は必ず `Visible = $false`＋処理後 `Quit()`＋プロセス終了確認まで行う

## 6. 品質チェック（文書系スキル共通）

文書生成後に以下の自己レビューを実施する:

1. **体裁チェック**: フォント統一、ページ番号、図表番号の連番
2. **文体チェック**: 「である」調 or 「ですます」調の統一
3. **参照チェック**: 図表への本文中の言及漏れがないか
4. **ファイル名チェック**: 命名規則に従っているか（「最終版」禁止。`safe_save_path` を通せば機械で止まる）
5. **出力先チェック**: 適切なディレクトリに保存されているか

## 7. 外部連携（MCP）の使い方（全文書スキル共通）

接続している連携は積極的に使ってよい（使える連携は環境ごとに違う。`claude mcp list` で確かめ、無ければ飛ばす）。**読み取り・検索は随時／書き込み・送信・予定追加・push は必ず確認を取ってから。**

- **Tavily 検索**: 事実・統計・市場規模・先行事例の裏取り。標準 WebSearch より日本語に強い。引用元URLを残す。
- **arXiv**: 論文・技術の一次情報（半導体・量子・最適化など）。出典を残す。
- **Google Drive**: 素材（資料・画像・既存ファイル）が Drive にある場合の取得元。
- **Google Calendar**: 予定・締切の参照（議事録/アジェンダの日時、報告書の日程）。
- **Gmail**: 連絡文の下書き・送信、関連メールの確認（送信は確認必須）。
- 取得した外部情報も **AIくさく書かない・捏造しない**。数値は出典付き、未確認は「要確認」と明記。

## 8. イシューからはじめよ（思考の型・全スキル共通）

出典: 安宅和人『イシューからはじめよ』。
**きれいな成果物から入らない＝「犬の道」を避ける。** report / proposal / slide-gen / es / 各レポート系、
課題解決（デバッグ・レビュー・設計）など「考えて何かを出す」系スキルは着手前に必ずこの型を通す。

1. **イシューを1文で言い切る**：このアウトプットで *答えを出すべき問い* を1文に。「〜について書く」ではなく
   「〜すべきか?」「なぜ〜なのか?」「A と B どちらか?」という *問いの形* にする
2. **良いイシューの3条件**で吟味：①本質的な選択肢（答えると次が決まる分岐点）②深い仮説がある
   ③手持ちの素材で答えを出せる。満たさない問いは立て直す（＝イシュー度を上げる）
3. **仮説＝答えを先に置く**：その問いへの自分の答え（言いたいこと）を一文で先に決める。これが核になる
4. **サブイシューに MECE 分解**（3つ程度）：重複・漏れを点検
5. **ストーリーラインで並べる**（結論ファースト：WHY型／空・雨・傘型／PREP型のいずれか）
6. 各パーツに **「So What?（だから何?）」** が言えるか確認。言えなければ統合 or 削除

> **コード系スキルでの読み替え**：「イシュー」＝*本当に解くべき問題（真因・要件）*。
> 症状や実装の前に「何が問題で、解けたらどう確かめるか」を1文で固定してから手を動かす。

## 9. AIっぽさ撲滅レイヤー（全スキル共通）

人に読ませる文章を生成するスキル（report / es / proposal / email / zenn / 各報告書 / slide-gen 等）は、
出力前にこのレイヤーを必ず通す。AIくささを消すスキルを別に入れていれば、その書き換え観点も使う。

### 量産コピーを禁止（言葉のAIくささ）
- **NG表現**（抽象・どの文脈にも当てはまる定型句）:
  「〜を加速」「〜を最適化」「〜を実現」「〜に貢献」「今の時代」「無限の可能性」「シナジー」「DX推進」
  「次世代の」「革新的な」「さらなる」「〜と言えるだろう」「〜が重要である」「〜が求められる」「Overview」「Key Takeaways」の乱用
- **OK**: 具体シーン・固有名詞・before/after の数値（「3時間 → 5分」）・身近換算（「クラス40人なら○人」）
- 主張は **一文で言い切る**（結論ファースト、冗長な前置きを削る）
- **主題・主語を省かない**: 「〜は〜です」の「〜は」を抜かない。課題・報告書の答えは設問の対象を頭に置く
  （「この事件の概要は、〜ことです。」）。「その」「それ」が指す物が1つに決まらない所は名詞で書く。
  口語らしさやこそあどより、答えとして成立することが先（運用で出た指摘）

### 意味が1通りに決まる文（2026-10-01 本人「結局何を言いたいのか伝わらない」）
元の資料は Kiminori Yokoi「AI臭い文章とは何なのか」（豊洲会 2026-09-28・https://speakerdeck.com/nasuvitz/ai-kusai-bunshou-toha-nanina-no-ka ）。
AI臭い文章は「日本語がおかしい文章の一種」で、読み手に文脈の補完を求める。特徴は3つ。
1. **不要な対比・否定・留保から入り、主文を直接書かない**（「〜ではなく」「単なる〜ではない」「重要なのは、」「結論から言うと」、短い否定文の直後の短い肯定文）
2. **抽象語や比喩の動詞で、何をするのかが曖昧**（〜側に倒す・前提が崩れる・静かに壊れる・時間を溶かす・地味に効く・原因を潰す・深掘り）
3. **短文・対句・不自然な読点・名詞化で、内容以上に印象的に見せる**（「前提を、」の溜めの読点・語を入れ替えた反復・「〜の効率化」で止める）
- 判定の問い：**書き手の説明なしに、この文だけで「誰が・何を・どうした」が1通りに決まるか**。決まらない語には「これってどういう意味？」と聞き、答えの文をそのまま本文にする（資料の会話の型）。
- 文を短くする時に削るのは、無くても意味が変わらない語だけ。主語・目的語・条件・数字は削らない。
- 人の文章を「AIくさい」と指摘する時も、語を引用し、読み手が何を補わされるかと書き直しの文まで言う（「AIくさい」自体が抽象的な指摘）。
- 機械では check_ai_likeness（report の実験レポート）・slide-gen の意味の検査（スライド）が型を拾う。スライドは加えて slide-reader（ノートを見ない初見の読み手）が文字だけで言い直せるかを判定する。

### 文のリズム・身の丈
- 文末・文長を単調にしない（同じ語尾の連続、機械的な三段構造を崩す）
- 箇条書きに逃げず、地の文で書くべき所は書く
- 本人の身の丈・知識量に正直に（背伸びした流暢すぎる文＝AIくささ。応募書類・英作文では特に厳守）

### コード系スキルでの読み替え
- 説明文・コメント・コミットメッセージ・PR本文に「〜を実現」「堅牢な」「シームレスに」等の
  中身のない美辞麗句を使わない。何をなぜ変えたかを具体語で書く

> 仕上げに「この文、AIが書いたとバレないか? 本人が書いたように読めるか?」を1度セルフチェックする。

**機械チェック（任意）**: AIくささの機械検査スクリプト（定型句・文末の3連続・接続詞の連発などを行番号付きで拾う物）を
持っていれば、下書きを一時ファイルに書いて回し、0件になるまで直す。**このリポジトリには含まれない**ので、
無ければ上の NG 表現と「判定の問い」で目視で点検して先へ進む（ここでスキルを止めない）。
report は専用パイプライン（`run_pipeline.py` の check_ai_likeness）で足りる。

## 10. スキル使用の公言（全スキル共通・必須）

スキルを実行するときは、**応答の冒頭で必ず**「📢 ◯◯スキルを使っています」と公言する
。
- 形式: `📢 {スキル名} スキルを使っています`（必要なら括弧で適用レイヤーを添える。
  例: `📢 report スキルを使っています（イシューからはじめよ＋AIっぽさ撲滅を適用）`）
- 内部参照専用の shared-doc-rules 自体は直接実行されないため公言不要。
