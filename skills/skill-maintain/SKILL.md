# skill-maintain — スキル自動保守メタスキル

> **▶ 実行開始時の共通3点セット**（詳細 → `~/.claude/skills/shared-doc-rules/SKILL.md` §8〜§10）
> 1. 📢 **公言**：応答冒頭で「skill-maintain スキルを使っています」と必ず出力する（§10）
> 2. 🎯 **イシューからはじめよ**：点検の前に「今いちばん直すべき不整合は何か」を見立ててから動く（§8）
> 3. 🚫 **AIっぽさ撲滅**：報告文に定型句を使わず、old→new を具体語で書く（§9）
> 4. `~/.claude/skill-memory/skill-maintain.md` を読み込む

`~/.claude/skills/` 配下の全スキルを点検し、CLAUDE.md の最新構造との「つながり」を保つ。

実行開始前に:
1. `~/.claude/skill-memory/skill-maintain.md` があれば読む
2. プロジェクトの CLAUDE.md を読み、**現在の正しいフォルダ構造・出力先・命名規則**を基準にする

---

## STEP 0: 一発自己診断（必ず最初に）

```bash
py ~/.claude/skills/skill-maintain/scripts/selftest.py   # 構造/参照/旧パス/断言/競合/compile/メモリリンクを機械判定
py ~/.claude/skills/skill-maintain/scripts/selftest.py --skills <スキルのフォルダ>   # ~/.claude/skills 以外を見る時
```

ワークスペースを環境変数 `CLAUDE_WORKSPACE` で渡すと、その CLAUDE.md の旧パスと競合コピーも見る（無ければその検査は SKIP と表示して飛ばす）。
ほかの環境変数（`CLAUDE_PROJECT_MEMORY` 等）は selftest.py の冒頭に書いてある。

PASS なら観点1〜7の手動監査は差分だけでよい。FAIL の行がそのまま修正リストになる。

## STEP 1: 点検（7観点）

各スキル（`$ARGUMENTS` 指定があればそれのみ、無ければ全 SKILL.md）について確認:

1. **古いパス/フォルダ参照** — CLAUDE.md の現構造と矛盾するパスを検出。
   - 例（作者の構成で番号付きフォルダに改名した時）: 番号無しの `学内/`→`10_学内/`、`授業/`→`10_授業/`、`ツール/`→`40_ツール/`、`_受信箱`→`90_受信箱`、`_ゴミ箱`→`99_ゴミ箱`、廃止したツールへの参照。
   - 検出は **パス区切り（`/ \ _`）でアンカー**して行い、散文中の同名語（「授業内容」等）は変えない。
2. **壊れた相互参照** — 存在しないファイル・スキル・`[[リンク]]`先。`~/.claude/skills/` とワークスペースで実在を確認。
3. **skill-memory の肥大・矛盾** — `~/.claude/skill-memory/{name}.md` が上限（1スキル10件、学習ログ型は例外）超過、または確定ルールと矛盾する古い記述の温存。
4. **自動選択(routing)の弱さ** — description にユーザーが言いそうなトリガー語が無い／曖昧で、発話からスキルが選ばれにくいもの。
5. **連携(MCP)の記述ずれ** — 各スキルの「連携(MCP)」記述や shared-doc-rules §7 が、連携の現状（接続済/未認証。CLAUDE.md に表を置いているならその表）と矛盾していないか。`claude mcp list` の実態と突き合わせる（例: 未認証なのに「接続済」と書いている／削除したサーバーを参照している）。
6. **3点セットの欠落** — 各スキル冒頭に「▶ 実行開始時の共通3点セット」（📢公言 §10・イシューからはじめよ §8・AIっぽさ撲滅 §9）があるか。無いスキル、または 📢 公言の指示が抜けているスキルを検出して補う。種別に応じてブロックを出し分ける（TEXT系=全3層／CODE系=公言+イシュー+説明文のクリシェ禁止／UTILITY系=公言+軽め）。内部参照専用の `shared-doc-rules` は実行されないため対象外。
7. **標準構造 v2 への準拠** — SKILL.md は骨子だけにし、長文資料は `references/`、実行コードは `scripts/`、静的素材は `assets/` に置く形。チェック項目:
   - SKILL.md が肥大していないか（目安150行超・長いコード/テンプレのインライン埋め込み）→ `references/`（長文資料）と `scripts/`（実行コード）へ分離し、SKILL.md には参照リンクを残す。
   - コードの直置き（SKILL.md と同階層の .py 等）や `assets/` へのコード混入 → `scripts/` へ移動。**移動時は SKILL.md 内のパス・スクリプト間 import・skill-memory の参照を必ず追従させ、`python -m py_compile` で構文検証する。**
   - スクラッチ・出力物（`_out*`・`__pycache__`・テスト生成画像・`.letta/` 等のセッション残骸）の混入 → ゴミ箱フォルダ（作者の構成では `99_ゴミ箱/{日付}/`）へ退避。

> 規模が大きい場合は「1スキル=1エージェント」で並列点検してよい（各エージェントは1つの SKILL.md だけを読み、修正案を構造化して返す）。ファイルが1対1なので競合しない。

## STEP 2: 重要度づけして提示

検出を **高/中/低** で分類し、`old→new` の具体修正案つきで一覧化。高（壊れた参照・古いパス）は即修正、中低は確認のうえ修正。

## STEP 3: 修正

- パス参照は **アンカー付き正規表現**で安全に置換（プローズを壊さない）。`開発/`・`授業/` のように散文衝突がある語は、パス文脈だけを個別修正する。
- description のトリガー語を補強（/skill-new STEP 1 の方針）。
- skill-memory は確定ルールを SKILL.md 本体へ昇格し、メモは「未解決・最新差分」だけ残す。
- 修正後、`/transcribe` `/report` 等が**実際に正しいフォルダへ出力するか**をパスの観点で確認。

## STEP 4: 完了

1. 修正内容を簡潔に報告（何を old→new したか）。
2. `~/.claude/skill-memory/skill-maintain.md` に今回の発見パターンを追記（次回の検出を速くする）。

## 注意事項

- **CLAUDE.md が常に正**。スキルを CLAUDE.md に合わせる（逆ではない）。構造が変わったら CLAUDE.md を先に直し、その後このスキルで波及修正する。
- 憶測で無関係な変更を増やさない。検出→提示→修正の順を守る。
- 大量リネーム後の参照追従はこのスキルの主用途。フォルダ名を変えたら必ず実行する。
- ripgrep は look-around 非対応。アンカー検出は PowerShell 等で `[regex]` を使う。
- **一括修正前に必ずバックアップ**: `tar czhf ~/.claude/skill-audit/backups/{日付}.tgz -C ~/.claude skills skill-memory hooks scripts agents CLAUDE.md`（無いフォルダは外す）。**`agents` を忘れない**（漏らすと復元時にエージェントが消える）。skills 等をジャンクション／シンボリックリンクにしている時は `-h` 必須（付けないとリンクだけ格納され中身が空になる）。
- **OneDrive の罠3件**（スキルを OneDrive で同期している場合）: (1) 未ハイドレートのファイルは `wc`/`cat` でハングする。棚卸しは `find -printf '%s\t%p\n'`（メタデータのみ）＋ `__pycache__` prune。(2) 同期稼働中に同一ファイルへ連続 Edit すると競合で `SKILL-{ホスト名}.md` にリネームされ元名が消えることがある。**大規模一括編集は、全ファイルをハイドレート後に OneDrive を一時停止（`taskkill /f /im OneDrive.exe` と `OneDrive.Sync.Service.exe`）してから行い、完了後に再起動して一括同期させる。**(3) 競合コピー（`*-{ホスト名}.md`）を見つけたら中身を比較し、新しい方を正の名前に戻す。
